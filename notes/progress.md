# Дневник: разбираемся с OpenXRay на Apple Silicon

Этот файл — точка возобновления работы. Что обсуждали, что в репо, и с чего продолжить.

## Что уже сделано в репо

- **`CLAUDE.md`** — обзор проекта целиком: что за движок, как собирать (CMake + MSBuild), конфигурации сборки (Debug/Mixed/Release/ReleaseMasterGold), как запускать, какие CI-проверки стиля, архитектурная карта модулей `xr*`, ключевые правила кодстайла. Это «учебник» по репо — открывай, когда нужно вспомнить общее устройство.
- **`notes/apple-silicon.md`** — итоги расследования по ARM64-проблемам: где в коде есть ARM-специфика, какие места подозрительные (FPU control в `_math.cpp`, `sse2neon` в горячих путях, `PlatformApple.inl` как копия Linux), и пошаговый план разбора с примером FPCR-патча.
- **`notes/progress.md`** (этот файл) — журнал работы.

## О чём говорили (короткое summary)

1. **Исторический контекст.** OpenXRay — это форк X-Ray Engine 1.6.02 (Call of Pripyat, GSC Game World). Ядро кода написано в 2001–2009 годах, поверх него с 2014 года живёт OpenXRay-сообщество. Отсюда смесь старого C++ (Hungarian, BOOL, свои контейнеры) и нового (C++17). Это нормально для такого проекта.
2. **Игра ≠ движок ≠ данные.** В репо только движок. `gamedata` (модели, текстуры, локации) и Lua-скрипты — собственность GSC, лежат у игрока на диске. Движок без них бесполезен.
3. **Старт исполнения** — `src/xr_3da/entry_point.cpp` → `CApplication::Run()` (в `xrEngine`) → главный игровой цикл (ввод → обновление мира → рендер → звук → следующий кадр).
4. **Состояние Apple Silicon** — формально поддерживается, по факту не оттестировано. CI собирает arm64-macOS, но не запускает. Подозрительные места перечислены в `notes/apple-silicon.md`.
5. **Подход к MVP** — определить узкую цель (например, «дойти от старта до Скадовска без падений»), сделать стабильный repro краша, собирать в `Mixed`+ASan, запускать под `lldb`, категоризировать падения по модулю в стектрейсе, атаковать одну группу за раз. Не пытаться «починить всё».

## Что делать в следующий раз (первая сессия после клонирования)

**Цель сессии: собрать проект, убедиться что бинарь нативный arm64, попробовать запустить.**

### Шаг 1. Подтянуть всё локально

```bash
git clone --recursive <repo-url> xray-16
cd xray-16
# или, если уже клонировал без --recursive:
git submodule update --init --recursive
```

`--recursive` важно — без подмодулей CMake упадёт с явной ошибкой.

### Шаг 2. Установить зависимости через Homebrew

```bash
brew install cmake sdl2 lzo libogg libvorbis theora jpeg-turbo openal-soft
```

`openal-soft` — потому что встроенный macOS OpenAL устарел и движок может не подружиться. Остальное — из CI-конфига `.github/workflows/cibuild.yml`.

### Шаг 3. Сборка (Mixed, не ReleaseMasterGold)

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Mixed -DCMAKE_UNITY_BUILD=ON
cmake --build build --parallel
```

Почему `Mixed`, а не `ReleaseMasterGold`: с ассертами, но оптимизирован. Когда что-то ломается — увидим внятное сообщение, а не silent corruption.

### Шаг 4. Проверить, что бинарь arm64-нативный (ключевая проверка)

```bash
file build/bin/arm64/Mixed/xr_3da
# Должно быть: Mach-O 64-bit executable arm64
# Если: Mach-O 64-bit executable x86_64 — значит собралось под Rosetta, дальше нет смысла идти, надо разбираться с toolchain (скорее всего, x86-Homebrew)
```

Если путь к бинарю отличается — `find build -name xr_3da` найдёт его.

Дополнительно проверить, что и cmake, и компилятор — arm64:
```bash
arch     # должно быть arm64
which clang && file $(which clang)
which cmake && file $(which cmake)
```

### Шаг 5. Запустить с купленной/установленной игрой

Нужен `fsgame.ltx` от игры. Указывает движку, где лежит `gamedata`.

```bash
cd build/bin/arm64/Mixed
./xr_3da -fsltx /path/to/fsgame.ltx -nointro
```

`-nointro` пропускает заставки — быстрее доходим до меню.

По умолчанию запускается CoP. Для CS — флаг `-cs`.

### Шаг 6. Что записать по итогам сессии

Чем больше данных соберём в первый раз, тем быстрее дальше:

- [ ] `file` на бинарь — он arm64?
- [ ] Собрался ли проект целиком, или какой-то модуль упал? Если упал — какой и какая ошибка.
- [ ] Запустилось ли вообще, или сразу краш?
- [ ] Если запустилось — дошло ли до меню? До игры? Сколько прожило?
- [ ] **Скопировать `~/Library/Logs/DiagnosticReports/xr_3da*.ips`** — это macOS crash report, в нём виден модуль падения и стектрейс.
- [ ] **Скопировать engine log** — пишется рядом с `fsgame.ltx` в подкаталог `logs/`.
- [ ] Конкретный воспроизводимый сценарий: «после Х шагов / в локации Y / при действии Z → падает».

Положить всё это в `notes/session-N.md` следующим заходом — и от этого уже строить план дальше.

## Что НЕ делать в первой сессии

- Не пытаться сразу применять FPCR-патч из `notes/apple-silicon.md`. Сначала зафиксируй **baseline-поведение** без изменений. Иначе не отличишь, что починилось от твоего фикса, а что — от случайного сочетания факторов.
- Не лезть в код. Цель первой сессии — **окружение и repro**, а не разработка.
- Не собирать `Debug` сразу — он сильно медленнее. `Mixed` даёт 90% диагностики при разумной скорости.
