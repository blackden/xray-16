# Code-craft — 8 принципов изящного кода

Это не закон, не правила, и не «MUST follow». Это **чек-лист** который помогает
выбрать между подходами, когда дизайн неоднозначен. Если предложение нарушает
один из принципов — это сигнал что нужно лучше обосновать или пересмотреть,
не повод сразу отказаться.

Сформирован в ходе A.7.1 + A.7.2 рефлексии (2026-05-28). Каждый принцип
сопровождается примером из реальной работы над xray-16 — чтобы потом проще
было вспомнить «где мы это уже видели».

## 1. Одно место правды

У важной информации — **один** хранитель, не два. Если две переменные «должны
быть равны» — они рано или поздно разойдутся, и баг ловить будешь долго.

**Пример из A.6**: наш атомный флаг `g_textInputActive` И `SDL_IsTextInputActive()`
держали один и тот же факт «консоль открыта». Каждое включение/выключение
обновляло оба. Один пропустишь — gate desynced. В A.7.2 мы выкинули SDL gate,
оставили только наш atomic bool. Правда одна.

**Сигнал нарушения**: «эти два значения должны быть согласованы», «не забыть
обновить обе», «в этой ветке кода они расходятся».

---

## 2. Симметрия — что открыл, закрой

Что открыл — закрой. Что включил — выключи. Что захватил — отпусти. Если есть
`Activate` — должна быть `Deactivate`. Если делаешь `+1` — где-то должен быть
`-1`. Несимметричный код легко прячет баг.

**Пример из A.7.2**: `OpenXRay_NativeTextInput_Activate()` вызывал
`[sTextInputContext activate]`, но `OpenXRay_NativeTextInput_Deactivate()`
имел только `[sTextInputContext deactivate]` без отмены побочного эффекта
process-wide registration. Activate без полноценного антипода = постоянный
эффект, не временный. Решение — оба убраны, симметрия восстановлена через
**ничего не делаем**.

**Сигнал нарушения**: function называется `Start/Open/Capture/Acquire/Enable`
— ищи пару `Stop/Close/Release/Free/Disable`. Если её нет — design smell.

## 3. Договор важнее реализации

Сделай **интерфейс** — список функций которые слой обязан предоставить —
отдельно от того **как** он это делает. Верхний слой работает с интерфейсом,
нижний его реализует. Меняешь нижний — верхний не трогаешь.

**Пример из A.6 + A.7.2**: `ITextInputBackend` — договор «вот функции для
ввода текста» (Start, Stop, IsActive...). Под Linux — `SDLTextInputBackend`.
Под macOS — `NativeTextInputBackend`. `CConsole` не знает который реализован
сейчас — она зовёт интерфейс. В A.7.2 мы поменяли **весь нижний слой** на
macOS; консоль не изменилась ни на строку.

**Сигнал нарушения**: код одного модуля проверяет `#ifdef XR_PLATFORM_APPLE`
чтобы решить **как** работать с другим модулем. Этот `#ifdef` должен жить
в реализации интерфейса, не в потребителе.

---

## 4. Дёргать самому vs отдать управление

Когда работаешь с библиотечным объектом — спроси себя: я его дёргаю по своему
ритму или я ему отдаю контроль (он сам решает когда меня позвать)? Первое —
больше работы, но всё прозрачно. Второе — короче код, но непредсказуемо.

**Пример из A.7.2 (landmine)**: `NSTextInputContext.activate` отдавал AppKit'у
контроль — «управляй сам когда надо звать наш `insertText:` callback». AppKit
начал звать его параллельно к нашему ручному `handleEvent:` — двойной dispatch,
каждый символ ввода удваивался. Убрали activate — AppKit перестал лезть
самовольно, мы дёргаем `handleEvent:` сами в нужный момент. **Меньше магии =
больше контроля.**

**Сигнал нарушения**: код делает что-то когда «непонятно когда» — фоновый
поток framework'а решает. Если не можешь объяснить «вот в этом месте этот
callback **точно** выстрелит» — это ownership-style, и оно когда-нибудь
выстрелит не там где ждёшь.

## 5. Каждый слой знает только соседей

Если код модуля A заглядывает в потроха модуля C, минуя B — это «протечка
абстракции». Завтра C поменяется внутри — A сломается, потому что зависел от
того что не должен был знать.

**Пример из A.7.2 (что бы было плохо если бы мы нарушили)**: `CConsole` мог бы
читать SDL events напрямую через `SDL_PollEvent` — тогда каждая фаза A.7.X
переписки backend'а ломала бы консоль. Вместо этого `CConsole` зовёт
абстрактный `IR_OnTextInput(text)` и не знает SDL ли это, native ли это,
что-то другое. Один слой между ними изолирует изменения.

**Сигнал нарушения**: `Module_A.cpp` `#include "Module_C/private_impl.h"`.
Или функция модуля A знает о внутренних константах модуля C.

## 6. Если строку можно удалить — её не должно быть

Каждая строка кода несёт вес. Если её удалил и что-то сломалось — она нужна.
Если удалил и всё работает — строка была мёртвая, она не должна была быть.

**Пример из A.7.1**: удалили 130 строк DIAG6 instrumentation. Они свою работу
сделали — нашли root cause #162. Дальше — мусор. Каждая такая строка
увеличивает когнитивную нагрузку на чтение, маскирует реальную логику.

**Пример из A.7.2**: удалили одну строку `[sTextInputContext activate]`. Она
**вредила** — создавала double dispatch. «На всякий случай оставлю» здесь
было бы катастрофой.

**Сигнал нарушения**: «оставлю на будущее», «вдруг пригодится», «чтобы не
поломать другой код». Это не аргументы — это deferred decision. Решай
сейчас: нужно (оставь с обоснованием) или нет (удали).

---

## 7. Простота требует больше думать, не меньше

Простой код не быстрее писать — он **дольше** пишется. Думаешь больше → строк
меньше → читать проще → менять легче. Это обратное к метрике «строк в час».

**Аналогия из DevOps**: terraform который влезает в один экран — ты
контролируешь систему. Terraform на 5000 строк — система контролирует тебя.
Hashi-stack infra-as-code хорош именно потому что заставляет думать
декларативно, а не накапливать императивные слои.

**В C++ engine** — то же самое. Меньше абстракций, меньше глобалов, меньше
специальных случаев = легче рассуждать. Хорошая функция помещается на экран.
Хороший класс имеет одну ответственность.

**Сигнал нарушения**: «пишу быстро, потом подчищу». Подчистки не будет.
Грязный код накапливается с накопительным эффектом.

## 8. Костыли копят, структурный фикс выкидывает

Костыль — локальный workaround, работает прямо здесь и сейчас, но не убирает
причину. Структурный фикс убирает причину — и связанные баги схлопываются сами.

Костыли копят: один → следующий баг требует второй костыль вокруг первого →
третий → cascade грязи. Структурный фикс дороже сейчас — но дальше всё проще.

**Пример из A.6 → A.7**:
- A.6 накопил костыли: `flush-on-resume hack`, `NONUSBACKSLASH alias`,
  `DIAG6 instrumentation`, `runSDLDrain skip logic`, `SDL_PumpEvents re-entry
  trap`. Каждый локально работал. В сумме — хрупкий слой.
- A.7.2 структурный фикс: native NSTextInputContext полностью убрал SDL
  participation в text-input pathway. Все 5 костылей умерли естественной
  смертью одной правкой контракта. -130 строк суммарно за фазу A.7.1.

**Сигнал нарушения**: «добавим ещё один флаг чтобы обойти», «там временный
workaround», «потом отрефакторим». Это значит причина не понята. Стоп.
Прежде чем добавлять костыль — попробуй понять корень.

## Как использовать этот документ

1. **Когда обсуждаем подход** — пробежать по 8. Если ни один не задевается,
   подход скорее всего ок. Если задеваются 1-2 — обсудить trade-off явно.
   Если задеваются 3+ — переосмыслить.
2. **Когда review code** — особенно принципы 1, 2, 6 легко проверить
   механически.
3. **Когда наследуем legacy** — принципы 7, 8 объясняют **почему** legacy
   накопил то что накопил, и **как** систематически разгребать.
4. **Когда mentoring** — конкретные примеры из A.6/A.7 дают material для
   in-band обучения (см. `mentor-principles.md`).

Принципы — **не догма**. Все они допускают исключения с обоснованием.
Цель — сделать обоснование **осознанным**, а не дефолтным.
